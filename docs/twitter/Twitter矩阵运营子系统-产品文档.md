## 一、文档定位

本文档用于定义当前大项目内 `Twitter/X 矩阵运营子系统` 的产品边界、架构方向、Agent 分工和首期落地范围。

这不是一个独立新仓项目，也不是对现有知乎系统的直接扩写，而是在当前大项目内部新增一条尽量独立、尽量隔离的业务线。

当前已确认的前提如下：

1. Twitter/X 子系统继续放在当前大项目里建设，不单独新开仓库。
2. 与知乎链路尽量隔离，避免影响现有已经相对稳定的知乎部分。
3. 当前共享能力只保留飞书通知，其他业务逻辑、数据模型、运行进程尽量独立。
4. Agent 架构采用 `主 Agent + 子 Agent` 的模式。
5. 子 Agent 除写作和发布外，新增一个调研型 Agent。
6. 调研结果需要沉淀为账户级 Markdown 文档，在每次写作前作为 Prompt 的补充材料读取。
7. 账户级 research 文档需要在前端展示，并允许用户微调。
8. 发布频率和连续发布节奏由 MainAgent 统一判断。
9. 整体策略尽量通过 LLM 约束，减少不必要的规则兜底。

## 二、项目背景

当前主项目已经围绕知乎形成了较完整的自动化链路，知乎模块目前的状态是：

1. 已有较稳定的运行流程。
2. 已具备持续迭代基础。
3. 当前阶段不适合再大幅改动核心链路。

但 Twitter/X 的运营目标和知乎不同：

1. 知乎更偏长内容沉淀与回答型表达。
2. Twitter/X 更偏高频短内容、线程表达、风格塑造和持续曝光。
3. 知乎的内容单元是 `问题 / 回答`，Twitter/X 的内容单元是 `帖子 / 线程 / 互动`。

因此，如果直接复用知乎的任务模型、状态枚举、数据结构和发布逻辑，会带来两个问题：

1. 模型语义不匹配，后续会越来越别扭。
2. 对现有知乎稳定部分形成回归风险。

本项目的核心思路不是“复制一套知乎系统”，而是：

在同一个大项目中，建设一个与知乎相互独立的 Twitter/X 子系统，只复用基础设施里真正通用的部分。

## 三、产品目标

### 3.1 业务目标

1. 建立一套适合 Twitter/X 的矩阵化内容运营流程。
2. 让不同账号形成明确但自然的表达差异，而不是简单换壳复用。
3. 在写作前加入主动调研能力，提升内容对平台语感、节奏和热点表达的贴合度。
4. 让 research 不只是回答“写什么”，还要回答“像谁学、学什么、学到什么程度”，帮助账户复制对标账号的灵魂。
5. 支持用户在前端查看并微调研究手册，避免系统输出成为黑盒。
4. 让内容从选题、调研、写作、审核到发布形成完整闭环。
5. 为后续的数据复盘和持续优化打下基础。

### 3.2 系统目标

1. 在当前大项目中新增一条独立的 Twitter/X 业务线。
2. 尽量不改动知乎现有核心链路。
3. 通过主 Agent 进行统一调度和质量把控。
4. 通过调研子 Agent 产出账户级写作补充文档。
5. 通过写作子 Agent 完成内容生成和改写。
6. 通过发布子 Agent 执行最终发布动作。
7. 飞书通知继续沿用现有能力。

### 3.3 非目标

1. 本期不做多平台统一抽象。
2. 本期不改造知乎已有发布链路。
3. 本期不做大规模自动互动。
4. 本期不追求复杂商业化编排和自动化增长实验平台。

## 四、产品原则

### 4.1 同仓开发，强隔离运行

Twitter/X 子系统继续放在当前大项目内，便于统一管理、统一部署和共享少量基础设施，但在业务实现上必须与知乎模块强隔离。

### 4.2 共享最小化

仅保留飞书通知等真正通用的基础能力复用，不直接复用知乎的业务模型、流程状态和发布逻辑。

### 4.3 主 Agent 负责决策，子 Agent 负责执行

主 Agent 负责选题分配、任务派发、审核把关、策略优化。子 Agent 只负责各自专业环节，不拥有最终发布决策权。

### 4.4 写作前先调研

写作不能只依赖基础 Prompt。每次写作前应优先读取最新的账户级研究文档，把平台语境、账号风格和近期有效表达方式引入写作上下文。

### 4.5 内容资产沉淀优先

真正重要的不只是生成一条帖子，而是不断积累：

1. 账户研究手册
2. 风格经验
3. 高表现表达方式
4. 失败表达的边界

### 4.6 API 优先，浏览器为辅

发布动作优先通过官方 API 完成。浏览器能力主要用于调研、观察、补充验证和少量例外场景，不作为主发布路径。

### 4.7 LLM 约束优先，规则兜底最小化

本系统尽量通过 LLM 完成以下约束：

1. research 结论提炼
2. 对标账号灵魂拆解
3. 写作风格控制
4. 质量审核
5. 发布频率判断
6. 线程拆分和连续发布节奏判断

规则兜底只保留在真正不能交给 LLM 的边界上，例如：

1. 授权状态
2. API 调用成败
3. 状态机合法性
4. 持久化写入
5. 通知发送

## 五、与知乎系统的关系和隔离策略

### 5.1 总体原则

Twitter/X 子系统属于当前大项目的一部分，但应被视为一条新的平台业务线，而不是知乎系统的一个分支功能。

### 5.2 共享部分

当前确定可以共享的能力只有：

1. 飞书通知
2. 少量基础设施，例如日志方式、环境配置读取方式、通用 LLM 封装

### 5.3 不共享部分

以下能力不应直接沿用知乎实现：

1. 知乎账号模型
2. 知乎选题发现逻辑
3. 知乎 `问题 / 回答` 数据结构
4. 知乎 Worker 流程状态
5. 知乎发布服务
6. 知乎登录态识别和页面语义判断
7. 知乎专用的数据库字段和任务语义

### 5.4 隔离要求

Twitter/X 子系统建议具备以下隔离边界：

1. 独立的应用入口
2. 独立的 Worker
3. 独立的数据模型
4. 独立的环境变量前缀
5. 独立的日志和运维进程名
6. 独立的账户配置与授权管理

### 5.5 产品层面的约束

1. Twitter/X 故障不应影响知乎 Worker 的继续运行。
2. 知乎模块应尽量维持当前稳定状态，不因 Twitter/X 接入而被迫调整核心逻辑。
3. Twitter/X 可以独立部署、独立暂停、独立排障。

## 六、目标用户和使用场景

### 6.1 目标用户

1. 运营负责人
2. 内容负责人
3. 产品负责人
4. 技术负责人

### 6.2 典型使用场景

1. 新建一个 Twitter/X 运营账号，定义其定位和目标受众。
2. 主 Agent 判断该账号需要什么类型的内容输出。
3. 调研子 Agent 先去做平台观察、风格采样和对标账号灵魂拆解。
4. 系统生成或更新该账号的研究手册 Markdown。
5. 用户在前端查看并微调该研究手册。
6. 写作子 Agent 在写作前读取研究手册和基础 Prompt。
7. 主 Agent 对稿件进行审核、打磨，并判断发布频率和连续发布节奏。
8. 发布子 Agent 执行发布。
9. 飞书同步关键信息给团队。

## 七、核心产品结构

本系统核心不是单次“生成推文”的工具，而是围绕账号持续运营形成的工作流系统。

系统的核心资产包括：

1. 账户级研究手册
2. 主 Agent 调度逻辑
3. 内容草稿与审核结果
4. 发布结果与后续复盘信息

其中，账户级研究手册是本期产品设计的关键新增资产。

## 八、Agent 架构设计

### 8.1 架构总览

系统采用以下角色分工：

1. `MainAgent`
2. `ResearchSubAgent`
3. `WriterSubAgent`
4. `PublisherSubAgent`

### 8.2 MainAgent

定位：全局调度与质量控制中心。

职责：

1. 根据账号状态和运营目标派发任务。
2. 判断某次写作前是否需要重新调研。
3. 给不同账号分配不同选题和切入角度。
4. 审核写作结果。
5. 给出改写建议。
6. 决定是否允许发布。
7. 判断发布频率、发布时间和连续长文的节奏。
8. 汇总发布结果，形成后续优化方向。

MainAgent 是唯一拥有最终放行权的角色。

### 8.3 ResearchSubAgent

定位：主动调研与知识沉淀中心。

职责：

1. 调研目标赛道与目标账号。
2. 观察近期高表现内容的开头方式、结构、语气和互动模式。
3. 观察目标受众的常见表达和平台语境。
4. 拆解对标账号在文风、结构、叙事习惯、内容组织上的“灵魂”。
5. 判断哪些灵魂特征适合当前账号学习，哪些不能直接照搬。
6. 形成账户级写作补充建议。
7. 输出或更新该账户的研究手册 Markdown。

ResearchSubAgent 的核心价值不在于“给一段建议”，而在于持续沉淀出可复用的账户级内容认知。

### 8.4 WriterSubAgent

定位：内容生产与改写执行者。

职责：

1. 读取基础 Prompt。
2. 读取账户研究手册。
3. 读取本轮 brief。
4. 输出单帖或线程草稿。
5. 根据 MainAgent 的意见进行改写。

WriterSubAgent 不应绕过 MainAgent 直接发布。

### 8.5 PublisherSubAgent

定位：发布执行者。

职责：

1. 仅接收已经审核通过的内容。
2. 调用 Twitter/X 官方 API 执行发布。
3. 返回发布结果、链接和错误信息。
4. 触发飞书通知。
5. 在必要时进入异常处理流程。

PublisherSubAgent 不负责写作优化，也不负责最终内容决策。

## 九、调研子 Agent 和账户研究手册设计

### 9.1 设计目标

为每个账号维护一份动态更新的研究手册，用于补充基础 Prompt，使写作更接近该账号应有的表达方式和平台语感。

这份文档不替代 Prompt，而是作为 Prompt 的补充层。

这份文档还有一个更直接的目标：

它要帮助系统回答“这个账号应该向谁学，以及应该学到什么程度”，而不是只回答“这个题怎么写”。

### 9.2 文档形态

每个账号维护一份独立的 Markdown 文档。

该文档应具备以下特点：

1. 可读
2. 可更新
3. 可版本化
4. 可直接被写作链路读取

### 9.3 文档作用

每次写作前，WriterSubAgent 需要先读取该文档，再结合基础 Prompt 和本轮 brief 生成内容。

它的作用类似于：

1. 账户级写作补充说明
2. 最新的平台表达观察记录
3. 该账号近期应该采用和避免的表达方式说明
4. 对标账号灵魂拆解结果
5. 用户人工微调过的风格偏好

### 9.4 建议内容结构

每份研究手册建议包含以下部分：

1. 账号定位
2. 目标受众
3. 近期调研摘要
4. 同类账号高表现表达拆解
5. 对标账号灵魂拆解与迁移边界
5. 推荐开头方式
6. 推荐的节奏和结构
7. 推荐词汇和语气
8. 不建议使用的表达
9. 可复用的论述框架
10. 当前阶段建议测试的表达方向
11. 风险提醒
12. 更新时间和调研范围
13. 用户微调备注

### 9.5 调研结果应体现的内容

ResearchSubAgent 不是只做事实收集，而要给出对写作直接有价值的观察，例如：

1. 什么样的开头更容易让用户停下来。
2. 哪些表达像真实用户，哪些表达像模板。
3. 目标圈层常用哪些说法。
4. 哪些句式已经被用滥。
5. 最近什么类型的话题更容易获得关注。
6. 当前更适合“观点型发帖”还是“经验型线程”。
7. 哪些表达方式容易引发反感或低质量互动。
8. 某个对标账号真正可迁移的不是哪些表层词汇，而是哪些底层写作习惯。

### 9.6 更新机制

研究手册的更新建议遵循以下规则：

1. 新账号接入时必须生成首版文档。
2. 如果文档过旧，写作前先更新。
3. 如果账号定位变化，应强制重写。
4. 如果近期内容效果明显变差，应触发调研刷新。
5. 用户在前端人工微调后，应保留人工修改结果，不应被下一轮 research 无条件覆盖。

### 9.7 前端展示与微调

research 文档不能只存在于后端文件系统或任务产物里，必须在前端可见。

前端应至少支持：

1. 查看当前版本 research 文档
2. 查看最近更新时间
3. 查看本轮更新原因
4. 对关键段落进行人工微调
5. 保存用户微调内容

用户微调后的文档应作为下一轮写作的正式输入。

### 9.8 与写作链路的关系

写作时的输入不再只有基础 Prompt，而应包括：

1. 基础 Prompt
2. 账户研究手册
3. 用户微调后的研究结论
4. 本轮选题 brief
5. 必要的历史表现摘要

## 十、内容单元设计

知乎的最终内容单元偏长回答，Twitter/X 的内容单元不应照搬。

本系统建议采用 `Post Pack` 作为一次写作任务的核心输出。

### 10.1 Post Pack 定义

一次内容任务最终输出的不是单一正文，而是一组可用于运营决策和发布执行的内容包。

### 10.2 Post Pack 建议组成

1. 主帖版本
2. 线程版本
3. 开头备选
4. 结尾备选
5. 可选 CTA
6. 首评建议
7. 话题标签建议
8. 风险备注

### 10.3 这样设计的原因

1. 同一主题在 Twitter/X 上可能更适合线程而不是单帖。
2. 不同账号对同一主题的承接方式可能不同。
3. 审核和运营更容易比较不同表达版本。

### 10.4 配图说明

配图能力不纳入 V1 MVP。

原因如下：

1. 当前最重要的是先把文本链路跑通。
2. 主 Agent、ResearchSubAgent、WriterSubAgent、PublisherSubAgent 的基本职责边界还需要先稳定。
3. 如果过早把配图纳入首期，会显著增加模板、审核、素材、发布和复盘复杂度。

因此，V1 统一按“纯文本优先”处理：

1. 支持单帖文本发布。
2. 支持线程文本发布。
3. 支持首评或补充文本建议。

配图相关能力延后处理，在后续版本单独规划，不进入当前 MVP 验收范围。

### 10.5 发布频率与连续发布策略

发布频率不由固定规则表直接决定，而由 MainAgent 结合内容结构、账号定位和平台表达方式统一判断。

截至 `2026-04-01`，X Help Center 仍将普通 Post 描述为典型 `280 characters` 上限，Premium 提供更长的 posts 能力，线程支持一次性 `Post all` 连续发出。因此本系统在产品策略上不把“长内容拆开发且中间留较长间隔”作为默认做法。

V1 采用以下原则：

1. 如果是一组连续表达的长内容，应优先拆成线程。
2. 线程内内容默认同批或连续发布，不人为拉开长间隔。
3. 同一主题的长文拆分，不建议隔天发成断裂内容。
4. 是否需要控制账号日更频率，由 MainAgent 综合判断。
5. 发布频率判断尽量交给 LLM，而不是写死成固定阈值。

## 十一、核心业务流程

### 11.1 标准流程

1. MainAgent 判断哪些账号需要运营。
2. MainAgent 给每个账号分配本轮目标和选题方向。
3. MainAgent 检查该账号研究手册是否需要更新。
4. 如需更新，由 ResearchSubAgent 先执行调研。
5. ResearchSubAgent 输出或更新账户研究手册 Markdown。
6. MainAgent 将 brief 派发给 WriterSubAgent。
7. WriterSubAgent 读取基础 Prompt 与账户研究手册后生成 Post Pack。
8. MainAgent 审核内容并提出修改意见。
9. WriterSubAgent 按意见改写正文。
10. MainAgent 决定是否批准发布。
11. PublisherSubAgent 执行文本发布。
12. 系统记录结果并发送飞书通知。

### 11.2 异常流程

1. 调研不足时，ResearchSubAgent 继续补样。
2. 文案不达标时，MainAgent 可退回重写。
3. 发布失败时，PublisherSubAgent 只回传错误，不自行改文。
4. 鉴权异常、限流或接口异常时，进入人工处理或后续补偿流程。

## 十二、功能模块设计

### 12.1 账户管理

1. 新建 Twitter/X 账号档案
2. 配置账号定位
3. 配置目标受众
4. 配置风格标签
5. 记录授权状态

### 12.2 调研中心

1. 发起主动调研任务
2. 浏览目标账号与高表现内容
3. 生成调研摘要
4. 更新账户研究手册
5. 支持对标账号灵魂拆解
6. 支持前端查看与微调

### 12.3 选题分发

1. 主 Agent 为不同账号分配不同切口
2. 减少矩阵同质化
3. 支持同主题多角度表达

### 12.4 写作中心

1. 根据研究手册和 brief 生成 Post Pack
2. 支持单帖和线程
3. 支持改写
4. 支持基于用户微调后的 research 文档写作

### 12.5 审核中心

1. 检查是否符合账号定位
2. 检查风格是否自然
3. 检查内容是否过于同质化
4. 决定是否发布
5. 判断本次内容应单帖发、线程发，还是不发
6. 判断连续内容的发布时间和是否需要留间隔

### 12.6 发布中心

1. 通过官方 API 执行发布
2. 记录发布结果
3. 触发飞书通知
4. 记录失败原因

### 12.7 复盘中心

1. 记录发布成功率
2. 记录不同账号的内容输出节奏
3. 为后续效果分析提供数据基础

## 十三、执行策略

### 13.1 工具策略

1. 发布主路径优先使用 Twitter/X 官方 API。
2. 浏览器能力主要用于调研和补充观察。
3. 不将浏览器自动化作为 Twitter/X 主发布路径。

### 13.2 Prompt 策略

写作输入采用双层结构：

1. 基础 Prompt
2. 账户研究手册

必要时再叠加：

3. 用户微调内容
4. 本轮运营 brief
5. 最近一次审核反馈

### 13.3 频率策略

1. 发布频率由 MainAgent 判断，不做简单固定频率表。
2. 对于本质上属于一篇连续长内容的表达，优先按线程处理，并在同一时段连续发布。
3. 不建议把一组强关联线程人为拆成跨天发布。
4. 是否压缩或放宽日更频率，交给 MainAgent 结合账号状态和内容目标判断。

### 13.4 LLM 约束策略

1. 风格控制优先由 LLM 完成。
2. 对标账号灵魂学习优先由 LLM 归纳。
3. research 文档更新优先由 LLM 生成和重写。
4. 审核和发布频率判断优先由 LLM 完成。
5. 规则兜底仅保留在授权、状态流转、持久化和接口错误等硬边界。

### 13.5 通知策略

Twitter/X 子系统继续复用现有飞书通知能力。

建议纳入通知的事件包括：

1. 发布成功
2. 发布失败
3. 授权异常
4. 研究手册更新完成
5. 审核阻塞

## 十六、主要风险

1. 如果研究手册更新太频繁，可能导致账号风格漂移。
2. 如果研究手册长期不更新，会退化成僵硬模板。
3. 如果主 Agent 审核不严，矩阵同质化仍会出现。
4. 如果发布链路绕过主 Agent，质量风险会迅速放大。
5. 如果与知乎共用过多业务结构，会影响已有稳定链路。

---

## 十七、当前结论

当前产品方向结论如下：

1. Twitter/X 子系统继续放在当前大项目内建设。
2. 与知乎部分强隔离，尽量不动现有知乎核心链路。
3. 当前明确共享的能力只保留飞书通知。
4. Agent 架构采用 `MainAgent + ResearchSubAgent + WriterSubAgent + PublisherSubAgent`。
5. ResearchSubAgent 的核心产物是账户级 Markdown 研究手册。
6. 每次写作前必须读取研究手册，作为 Prompt 的补充材料。
7. 发布动作采用 API 优先策略。
