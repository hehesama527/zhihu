## 一、文档目标

本文档用于把 `Twitter/X 矩阵运营子系统` 从产品方向收敛到可执行的 MVP 落地方案。

重点回答四个问题：

1. MVP 到底做哪些，不做哪些。
2. 落地顺序如何拆分。
3. 每一步的产物是什么。
4. 每一步如何验证，什么算通过，什么算不通过。

本文档是执行文档，不是愿景文档。凡是本期不进入 MVP 的内容，统一不纳入本轮验收。

## 二、MVP 范围冻结

### 2.1 本期必须做

1. `已完成` Twitter/X 子系统在当前大项目内独立落地。
2. `已完成` 与知乎链路尽量隔离，只共享飞书通知等最小基础能力。
3. `已完成` MainAgent 能完成任务派发和审核；Worker 主链路与人工审核入口都已接入正式 MainAgent 审核链路。
4. `部分完成` ResearchSubAgent 能生成和更新账户级 research Markdown 文档；文档生成、保存、前端微调已落地，但当前 research 依赖 simulated search，不是实时外部调研。
5. `已完成` 前端能展示 research 文档，并允许用户微调。
6. `部分完成` WriterSubAgent 能读取 research 文档并生成文本内容；主写作链路已落地，但质量差异和账号风格稳定性仍待实机验收。
7. `部分完成` PublisherSubAgent 能执行文本发布；当前实现采用浏览器自动化 / dry-run 发布链路，符合当前口径，但尚未完成真实发布验收。
8. `已完成` 系统具备最小可用的任务状态流转和异常处理能力；延期发布、重试、重排都已与“已批准内容直接进入发布”语义对齐。

### 2.2 本期明确不做

1. 配图能力
2. 自动化互动能力
3. 多平台统一抽象
4. 复杂数据回流
5. 高级实验系统
6. 大规模并发调度

### 2.3 本期验收目标

MVP 最终必须完成一条真实闭环：

1. 选定账号
2. 生成或更新 research 文档
3. 在前端查看并微调 research 文档
4. 基于文档完成写作
5. 主 Agent 审核并判断发布节奏
6. 调用浏览器自动化发布链路成功
7. 飞书收到结果通知

只要这条闭环没有跑通，MVP 就不能算完成。

当前结论：

1. 前 1-5 步已具备主路径雏形。
2. 第 6 步和第 7 步尚未完成真实验收。
3. 因此当前不能判定本期 MVP 已完成。

## 三点五、MVP 实现原则

### 3.5.1 LLM 约束优先

MVP 期尽量通过 LLM 解决以下问题：

1. research 文档生成
2. 对标账号灵魂拆解
3. 风格迁移控制
4. 文案审核
5. 发布频率判断
6. 线程连续发布节奏判断

### 3.5.2 规则兜底最小化

硬规则只保留在以下边界：

1. 账号授权
2. 状态流转
3. 发布链路调用结果
4. 持久化写入
5. 飞书通知

除此之外，不建议在 MVP 阶段堆太多静态规则表和复杂 fallback。

## 三点六、Agent 架构补充结论

### 3.6.1 当前判断

1. 当前采用的 `MainAgent + ResearchSubAgent + WriterSubAgent + PublisherSubAgent` 四层架构方向正确，可以继续沿用。
2. 当前主要问题不在“是否要拆多 Agent”，而在“各 Agent 的权限边界和流转语义还没有完全守住”。
3. 因此，本期不建议推翻现有架构重做，建议继续在当前架构上补齐关键缺口。

### 3.6.2 各 Agent 当前落地状态

| Agent | 文档目标职责 | 当前实现状态 | 结论 |
| --- | --- | --- | --- |
| `MainAgent` | 任务派发、研究审核、草稿审核、发布节奏决策、唯一发布闸门 | Worker 主链路与人工审核入口都已接入审核和发布计划生成 | `已完成` |
| `ResearchSubAgent` | 生成/更新账户级 research 文档，沉淀长期写作语境 | research 生成、保存、前端微调已落地，但当前依赖 simulated search | `部分完成` |
| `WriterSubAgent` | 读取 research 文档并生成 `Post Pack`，按审核意见改写 | 基本主链路已落地，可读取 research 并输出草稿 | `部分完成` |
| `PublisherSubAgent` | 接收已批准内容并执行发布，回写结果 | 已能 dry-run / 浏览器发布并回写结果，且已消费 `publishPlan.mode` 与延期节奏 | `部分完成` |

### 3.6.3 当前需要守住的架构边界

1. `已基本守住` 调研、写作、审核、发布已经拆成独立服务和独立数据结构，没有退化成单 Agent 全包。
2. `已修正` MainAgent 现在是唯一发布闸门，人工审核入口不会再直接越权改成可发布状态。
3. `已修正` PublisherSubAgent 已承接“已批准内容 + 节奏决策”输入，延期任务到点后会直接进入发布。
4. `已修正` 账号授权状态已成为运行时硬约束，登录校验失败不会再误判为可发布。
5. `当前建议` 保持四层 Agent 架构不变，后续重点转向真实发布验收和 research 能力边界，而不是重做架构。

### 3.6.4 架构验收结论

1. 如果只判断“架构设计是否正确”，当前结论是：`正确，可以继续沿用`。
2. 如果判断“架构是否已经被忠实落地并可验收通过”，当前结论是：`尚未完全通过`。
3. 本轮后续修正应以“让架构边界真正落到代码里”为目标，而不是继续扩功能面。

2. 已完成：人工审核入口会重新调用正式 MainAgent 审核，不再允许绕开审核上下文直接改成可发布。

### 9.1 目标

### 9.4 验证逻辑

验证问题：

1. MainAgent 是否真正控制了发布入口。
2. 审核意见是否可执行，而不是泛泛而谈。
3. 不合格内容是否会被拦下。
4. 同一组连续长内容是否会被合理判定为线程并连续发布。

通过标准：

1. 未通过审核的内容无法进入发布阶段。
2. 审核结果明确区分“重写”还是“重新调研”。
3. 审核意见能被 WriterSubAgent 或 ResearchSubAgent 继续消费。
4. 发布任务里能看到 MainAgent 给出的节奏决策。

不通过标准：

1. 审核结果只有“行 / 不行”，没有执行建议。
2. 草稿即使未审核也能被发布。
