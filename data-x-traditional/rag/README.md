# Traditional Account RAG

这套 RAG 只服务 `data-x-traditional` 链路，不影响 X Main，也不影响知乎链路。

当前版本的目标不是“做一个大知识库”，而是做一个**每个账户独立、可控、可逐步填充**的写作与审核辅助库。

它主要解决 4 个问题：

- 让 `writer` 更像这个账号本人会发出来的话。
- 让 `review` 更明确地知道什么叫 AI 味、什么叫真人感不足。
- 让不同账户的表达方式、数字习惯、审核标准分开。
- 先用规则和少量高质量样本提升文案质量，而不是一上来堆大量杂资料。

---

## 1. 当前怎么用

这套 RAG 目前只注入到两个阶段：

- `writer`
- `review`

不会注入：

- `main`

也就是说：

- `main` 仍然只负责选题。
- `writer` 会读取该账户自己的风格规则、数字表达规则、样本和反例。
- `review` 会读取该账户自己的审核标准、数字表达规则、反例和样本，判断草稿哪里还像 AI、哪里数字报得太满、哪里不像真人会发。

---

## 2. 目录说明

- `account-library-map.json`
  - 负责把运行时账号映射到独立的 RAG 库。
  - 以后如果你的真实 handle 不是 `account_a` / `account_b`，主要改这里。

- `accounts/<account_key>/manifest.json`
  - 定义这个账户有哪些 RAG 文档。
  - 定义某个文档服务于 `writer` 还是 `review`。
  - 定义某个文档适用于 `single` 还是 `thread`。

- `accounts/<account_key>/style_rules.md`
  - 这个账户自己的写作风格规则。
  - 重点回答：这个账号怎么说话，怎么起手，怎么收尾，什么不能写。

- `accounts/<account_key>/number_expression_rules.md`
  - 这个账户自己的数字表达规则。
  - 重点回答：什么时候该精确，什么时候该区间表达，什么时候只给方向。

- `accounts/<account_key>/review_rubric.md`
  - 这个账户自己的审核标准。
  - 重点回答：什么叫通过，什么叫 AI 味，什么叫要打回。

- `accounts/<account_key>/good_single_posts.jsonl`
  - 这个账户认可的单条优质样本。
  - 后续主要服务单条推文写作和审核。

- `accounts/<account_key>/good_threads.jsonl`
  - 这个账户认可的多条 thread 样本。
  - 后续主要服务 thread 写作和审核。

- `accounts/<account_key>/bad_posts.jsonl`
  - 这个账户明确不想要的反例样本。
  - 主要服务 `review`，帮助识别 AI 味、模板味、表格味。

## 3. 你应该优先找什么资料

先说原则：  
**不是“相关就放进去”，而是“真的能提升 writer/review 判断的才放进去”。**

推荐优先级：

1. 你自己明确认可、想模仿的真实 X 文案
2. 你自己改过很多轮之后觉得“终于对了”的文案
3. 你明确不认可、但又经常出现的烂文案
4. 你自己总结出来的规则

不推荐优先塞进来的资料：

- 大而全的行业报告
- 泛化新闻汇总
- 课程笔记
- 长篇研究文
- 你自己也没想清楚是否喜欢的内容

原因很简单：  
这个 RAG 当前不是用来“补知识”，而是用来**收紧表达质量**。

## 4. 每个文件应该找什么内容

### 4.1 `style_rules.md`

这里不放样本，放规则。

应该写的内容：

- 这个账号的身份定位
- 这个账号更像什么人，不像什么人
- 常见起手方式
- 常见收尾方式
- 偏好的表达动作
- 明确禁区

应该来自哪里：

- 你对这个账号的直接要求
- 你改文案时反复说过的话
- 你对“像/不像这个号”的稳定判断

不要写成：

- 空泛品牌介绍
- 大而全的价值观文章
- 长篇自我感动式说明

一句话理解：  
`style_rules.md` 负责定义“这个号像谁，不像谁”。

### 4.2 `number_expression_rules.md`

这个文件非常关键。

应该写的内容：

- 单条推文最多留几个硬数字
- thread 整体最多留几个硬数字
- 什么情况必须报精确数
- 什么情况更适合区间表达
- 什么情况只说方向，不报表
- 哪些写法一看就像在念表

应该来自哪里：

- 你对“AI 味太重”的直接反馈
- 你觉得“这段像在读数据表”的例子
- 你觉得“这段数字太满”的例子

一句话理解：  
这个文件负责解决“数字怎么说才像真人”。

### 4.3 `review_rubric.md`

这里也不放样本，放审核标准。

应该写的内容：

- 什么样的文案才算通过
- 什么问题算轻问题
- 什么问题算重问题
- 哪些结构一看就像 AI
- 遇到问题时应该怎么改

应该来自哪里：

- 你每次打回文案时真正的理由
- 你最常说的几个判断句
- 你对 account_a / account_b 的不同要求

一句话理解：  
这个文件负责让 `review` 不只是说“有 AI 味”，而是知道**具体为什么有**。

### 4.4 `good_single_posts.jsonl`

这是后面最重要的样本库之一。

应该找什么：

- 真实 X 单条推文
- 中文优先
- 读起来像真人，不像文章，不像教程，不像新闻摘要
- 能代表这个账号想要的节奏和密度

样本最好具备：

- 一个清晰判断
- 一到两个支撑点
- 手机端读起来顺
- 没有系统话术
- 没有为了完整而完整

不要放：

- thread 里拆出来的一条半成品
- 明显是课程宣传
- 明显是标题党
- 明显是广告
- 你自己看着也觉得太“装”、太“演”的内容

### 4.5 `good_threads.jsonl`

应该找什么：

- 展开自然的 thread
- 第一条有抓力
- 后续递进清楚，但不写成报告
- 每条之间像真人顺着说，不像提纲分栏

重点看这些能力：

- 怎么开头
- 怎么铺一个判断
- 怎么在中间补证据
- 怎么收束，不讲大道理

不要放：

- 太课程化的长 thread
- 太像行业周报的 thread
- 只是堆很多信息，没有一个清晰主判断的 thread

### 4.6 `bad_posts.jsonl`

这是反例库，不是垃圾桶。

只放“真的值得 review 学习怎么打回”的反例。

建议优先收这些问题：

- 像在念表
- 数字太密
- 太像报告
- 太像教程
- 开头像摘要
- 结尾像标准答案
- 明明是热点文，结果写成行业综述
- 明明是知识文，结果写成鸡汤

不要放：

- 纯粹内容观点和你不同的文案
- 只是题材不适合，但表达本身没问题的文案

一句话理解：  
`bad_posts.jsonl` 不是收“我不喜欢”，而是收“为什么这种写法会出问题”。

## 5. 两个账户分别该找什么资料

### 5.1 `account_a` 应该找什么

定位：知识分享、指标、策略、执行、误区。

优先找：

- 指标误区拆解
- 交易策略过滤条件
- 止损、盈亏比、结构判断
- “我怎么处理”的交易笔记
- 带一点参数，但不过度教学的内容

理想样本特征：

- 有干货
- 不像上课
- 有参数，但不是参数表
- 有边界感
- 更像交易者记录和判断

不要找：

- 纯课堂式教学
- “学会这个就够了”那种内容
- 大而全的基础科普
- 太像课程大纲的 thread

### 5.2 `account_b` 应该找什么

定位：热点、消息面、交易影响、历史映射。

优先找：

- 热点出来后，能快速翻译成交易影响的推文
- 用一个关键数据支撑判断的推文
- 不念表，但有证据
- 不搬新闻，而是给出取舍和排序
- 有“这事值不值得看”的感觉

理想样本特征：

- 先判断，后支撑
- 一条里数字不多
- 没有系统痕迹
- 更像交易者在消化信息，不像编辑在播报

不要找：

- 纯新闻搬运
- 整张表翻译
- 一口气报很多数字
- 完整分析报告式推文
- 明显 AI 生成味很重的热点文案

## 6. 初始建议收集量

一开始不用追求多，先追求干净。

建议第一批：

- `style_rules.md`
  - 先写满

- `number_expression_rules.md`
  - 先写满

- `review_rubric.md`
  - 先写满

- `good_single_posts.jsonl`
  - 每个账户先收 `10-20` 条

- `good_threads.jsonl`
  - 每个账户先收 `5-10` 条

- `bad_posts.jsonl`
  - 每个账户先收 `8-15` 条

如果你时间不够，优先级是：

1. 规则文件
2. `good_single_posts.jsonl`
3. `bad_posts.jsonl`
4. `good_threads.jsonl`

## 7. 样本怎么写进 JSONL

后面每一行放一个 JSON 对象。

推荐格式：

```json
{"id":"a_single_001","text":"很多人看 MACD 只看金叉死叉，我现在更在意它出现在什么位置。","notes":"开头直接给判断，不解释定义；参数少；像交易笔记。","mode":"single","topicTags":["indicator","macd","execution"],"voiceTags":["dry","sharp","trader_note"]}
{"id":"b_bad_001","text":"根据最新数据，BTC 单日净流出 2242 枚，7 日净流入 2723 枚，ETH 单日净流出 23158 枚……","notes":"典型念表，数据太满，像把结构化数据转成自然语言。","mode":"single","topicTags":["hotspot","etf","flow"],"voiceTags":["ai_smell","table_like","over_dense_numbers"]}
```

字段说明：

- `id`
  - 样本唯一 id

- `text`
  - 样本文案正文

- `notes`
  - 你为什么选它，或者为什么讨厌它
  - 这部分很重要，后面 review 很依赖这类说明

- `mode`
  - `single` 或 `thread`

- `topicTags`
  - 题材标签
  - 比如：`indicator`、`hotspot`、`etf`、`macd`、`risk_control`

- `voiceTags`
  - 语气/结构标签
  - 比如：`dry`、`sharp`、`casual`、`table_like`、`too_complete`、`ai_smell`

## 8. 选资料时的筛选清单

准备放进库前，建议先问自己：

- 这条真的像真人发的吗？
- 这条真的符合这个账户吗？
- 我是喜欢它的“内容”，还是喜欢它的“表达方式”？
- 如果把题材换掉，这条表达机制还值得学吗？
- 它会不会把 writer 带偏成课程文、报告文、新闻稿？
- 它会不会让 review 学会错误标准？

如果这些问题你自己都答不清楚，先别放进去。

---

## 9. 什么资料不要进库

尽量不要放：

- 你自己都不确定是不是好内容的文案
- 明显 AI 味很重但“看起来很完整”的内容
- 大而全的行业分析
- 只有知识，没有表达价值的资料
- 只是信息很多，但不适合 X 平台的材料
- 只是观点正确，但写法很差的材料

这个库不是“资料越多越好”，而是“越能收紧表达越好”。

---

## 10. 建议的收集顺序

建议按这个顺序往里补：

1. 先把三个规则文件补好
2. 先补单条优质样本
3. 再补反例样本
4. 最后补 thread 样本

这样做的原因很简单：

- 你现在最急的是把文案从 AI 味里拉出来
- 这个阶段单条比 thread 更容易看出问题
- 反例能更快帮助 `review` 收紧标准
