## 一、先说结论

这份文档回答的核心问题只有一个：

> 要不要把当前的 `X Research Agent v2-zh` 直接改成“市场热点调研 Agent”？

当前结论很明确：

1. **不改造现有 `ResearchAgent` 的核心职责。**
2. **保留它继续服务账号长期 research markdown。**
3. **热点能力独立拆为 `HotspotScoutAgent / XHotspotScoutService`。**
4. **热点链路独立运行，只有在热点转成任务后才进入主任务链。**

原因也很简单：

1. 当前 Writer 仍然依赖 `research markdown` 作为账号认知输入。
2. 当前 `x_research_agent` 研究的是“账号长期表达规律”，不是“最近 72 小时的市场事件”。
3. 热点监控更像常驻 scanner / ops 能力，不像按任务触发的一次性研究。

所以这次真正落地的主线不是“把 `x_research_agent` 变成热点 Agent”，而是：

1. 保留账号长期研究能力。
2. 新增独立热点池和热点研究链。
3. 让 MainAgent 在热点转任务之后再接管主链。

## 二、当前真实状态

截至 2026-04-06，这件事已经不是纯方案讨论，热点主干链路已经落地成 MVP。

### 2.1 `ResearchAgent` 现在实际做什么

当前 `XResearchService` 和 `x_research_agent` 的职责没有变，仍然是：

1. 读取账号基础信息、已有 research markdown 和任务上下文。
2. 基于 `simulatedSearchContext` 生成或更新账号长期研究文档。
3. 输出面向 Writer 的账号研究手册。

当前它**没有**做这些事：

1. 不做实时热点池扫描。
2. 不生成热点卡片。
3. 不维护 72 小时热点生命周期。
4. 不对新闻、行情、舆情对象做结构化研究。

这里要特别注意一个事实：

1. 当前 `ResearchAgent` 并没有接入实时联网搜索。
2. 它走的是 `simulatedSearchContext`，本质是方向性研究提示，不是真实热点抓取。

也就是说，它现在更像“账号长期研究手册生成器”，不是“热点研究器”。

### 2.2 热点链已经落地到哪一步

当前仓库里，热点链主干已经打通：

1. `x_hotspot_scout_agent` 已进入 Prompt 模板库。
2. `XHotspotScoutService` 已落地，负责扫描、去重、评分、补研究、转任务和清理。
3. 热点主存储已进入 MySQL。
4. `apps/x-api` 已提供热点池和 watchlist 的接口。
5. `apps/x-worker` 每轮 `tick` 先跑主任务链，再跑热点链。
6. 前端已提供：
   - `/twitter/hotspots`
   - `/twitter/watchlists`
7. `watchlist` 中的 `x_account` 已接入真实时间线抓取，复用 Playwright 登录态，不依赖官方 X API。

### 2.3 当前还是“双存储”

当前 X 子系统不是“全进数据库”，也不是“全在 JSON”。

现在是双存储状态：

1. 主任务链仍主要保存在 `data-x`：
   - `accounts.json`
   - `tasks.json`
   - `research-docs.json`
   - `research/*.md`
2. 热点链已经进入 MySQL：
   - `x_hotspots`
   - `x_hotspot_sources`
   - `x_hotspot_research_runs`
   - `x_hotspot_task_links`
   - `x_hotspot_watchlists`
   - `x_hotspot_watchlist_items`
   - `x_hotspot_scan_runs`

这意味着：

1. 账号、任务、research 文档仍然偏文件型存储。
2. 热点对象已经进入更适合筛选、排序、清理和统计的数据库存储。

## 三、为什么不该把 `ResearchAgent` 直接改成热点 Agent

### 3.1 研究对象根本不同

当前 `ResearchAgent` 研究的是：

1. 账号画像
2. 目标受众
3. 表达气质
4. 参考对象
5. 写作动作
6. 长期边界

热点链研究的是：

1. 最近发生的事件
2. 现在为什么值得看
3. 可以从什么角度响应
4. 有哪些风险和不确定性

这两个对象不是一回事。

### 3.2 运行方式也不同

`ResearchAgent` 更适合：

1. 低频更新
2. 面向单账号
3. 累积型文档
4. 服务 Writer 的长期输入

热点链更适合：

1. 高频扫描
2. 面向全局市场
3. 短生命周期对象
4. 先筛选、后研究、再决定是否转任务

### 3.3 直接合并会打断当前写作链

如果现在直接把 `research markdown` 改成热点研究：

1. Writer 会失去账号长期画像支撑。
2. Main 的研究判断会失焦。
3. 前端研究手册会变成混合容器，不清楚到底在看账号资产还是热点资产。

所以最稳的做法不是合并，而是拆开。

## 四、改造后的目标定义

这次改造后的目标可以收成一句话：

> 为 X 子系统新增一条独立于主任务链路的热点监控与研究链路，把最近 72 小时内值得响应的热点沉淀成可筛选、可分析、可复用、可淘汰的数据资产。

这条链路至少要满足五个条件：

1. 所有热点先入库，不是先推送再丢失。
2. 所有热点都能去重、评分、排序和追踪。
3. 所有高价值热点都能补一层研究结果。
4. 所有热点按 72 小时窗口自动淘汰。
5. 所有已进入任务流的热点都要保留快照，避免历史链路失真。

## 五、当前的热点链怎么跑

### 5.1 总体链路

当前热点链可以概括成：

```text
采集 -> 标准化 -> 去重/聚合 -> 评分 -> 入库 -> 补研究 -> 热点池 -> 转任务 -> 清理
```

### 5.2 采集源和频率

当前实现的扫描频率已经写在 `XHotspotScoutService` 里：

1. `market`：5 分钟
2. `news`：10 分钟
3. `watchlist`：60 分钟

当前最小可行集包括：

1. 新闻源
   - BlockBeats RSS
   - Cointelegraph RSS
   - Decrypt RSS
   - Bitcoin Magazine RSS
2. 行情源
   - Binance 24h ticker
3. watchlist 源
   - `x_account`
   - `symbol`
   - `keyword`
   - `source`

### 5.3 `watchlist` 中的 `x_account` 是怎么抓的

这部分现在已经不是占位逻辑，而是真实抓取：

1. 通过 Playwright 复用登录态。
2. 复用持久化 profile。
3. 通过时间线采集器抓取目标账号最近 tweets。
4. 不走官方 X API。

这一步和参考账号调研共用了同一套时间线抓取思路，但服务目标不同：

1. 参考账号调研服务 Writer 风格学习。
2. `watchlist.x_account` 服务热点发现。

### 5.4 去重和聚合策略

当前主思路是：

> 规则优先，LLM 补充

原因：

1. 去重是基础设施问题，要求稳定、可复现、可审计。
2. 完全交给 LLM 会让后续排障变得很难。
3. 热点量一旦起来，规则法比 LLM 更稳。

所以当前更合理的层次是：

1. 一级去重：规则
2. 疑难合并：后续可加 LLM 辅助
3. 主路径：仍然以规则结果为准

### 5.5 评分和优先级

当前热点链已经做评分和优先级判定，最终统一落到：

1. `score`
2. `priority`

优先级仍然按这四档理解：

1. `P0`：必须追
2. `P1`：建议追
3. `P2`：可选追
4. `DROP`：不追

### 5.6 热点研究输出

当前 `x_hotspot_scout_agent` 的输出不是账号研究 markdown，而是结构化热点研究结果，核心字段包括：

1. `summary`
2. `whyNow`
3. `recommendedAction`
4. `suggestedTaskTitle`
5. `suggestedTaskBrief`
6. `angles`
7. `risks`
8. `operatorHints`

这套输出主要服务三件事：

1. 运营判断值不值得追
2. 热点转任务时复用标题和 brief
3. 给 Main / Writer 提供更清晰的任务起点

### 5.7 热点怎么转成任务

当前已经支持“基于热点创建任务”。

一旦热点转成任务：

1. 系统会保留热点快照。
2. 后续链路进入主任务流。
3. MainAgent 才开始接管。

这一步非常关键，因为它保证了：

1. 热点链和主链职责分开。
2. 热点不会绕过 Main 直接推进写作和发布。

## 七、72 小时清理策略

### 7.1 当前原则

当前实现已经接入 72 小时清理逻辑，原则是：

1. 热点对象只保留近 72 小时窗口。
2. 同一热点再次命中时，刷新 `lastSeenAt` 和 `expiresAt`。
3. 清理的是热点主对象，不是任务链历史。

### 7.2 为什么任务快照必须保留

如果热点进了任务流，但没有额外快照：

1. 热点被清掉后
2. 任务历史就只剩一个引用
3. 后面无法复盘“这条内容为什么被创建”

所以当前策略里最重要的一点不是“删不删”，而是：

> 进入任务流的热点，必须先保留快照。

### 7.3 当前状态

现在这部分已经做到基础可用：

1. 热点链有过期清理。
2. 任务侧有热点快照。
3. 热点主表删除后，任务历史不会完全断链。

后面还能继续补的，是更精细的清理保护条件，而不是从零开始设计。

## 八、前端和运营入口

当前热点链已经有独立入口，不再塞回研究手册里：

1. `/twitter/hotspots`
2. `/twitter/watchlists`

这意味着运营侧已经可以直接做这些事：

1. 看热点池
2. 看分数和优先级
3. 看研究结果
4. 重新研究
5. 标记忽略
6. 直接创建任务
7. 配置和维护 watchlist

研究手册仍然保留，但职责已经收窄为：

1. 账号长期 research markdown
2. 参考账号调研入口

它不再承担热点池主容器的职责。

## 九、这次改造带来的明确收益

把 `ResearchAgent` 保留、把热点链独立出来，带来的收益很直接：

1. 不会打断当前 Writer 对账号研究手册的依赖。
2. 热点对象终于有了正式生命周期，而不是短暂提醒后丢失。
3. 运营可以先筛热点，再决定要不要转成任务。
4. 主链和热点链分开后，职责更清楚，后续迭代不会互相污染。
5. 72 小时窗口清理和任务快照可以同时成立，不会丢历史。

## 十、还没完成的部分

当前主干已经落地，但还有几类增强项没有做满：

1. 更精细的疑难事件合并。
2. 更丰富的外部数据源。
3. 更细的清理保护条件和运营指标。
4. 更完整的热点运营分析能力。
5. 主任务链与热点链的存储进一步统一，逐步收敛双存储状态。

这些已经不是“有没有热点链”的问题，而是“热点链下一步做多强”的问题。

---

## 十一、最终建议

如果只保留一句决策建议，我的结论还是不变：

1. **不要把当前 `ResearchAgent` 直接改成热点 Agent。**
2. **保留它继续服务账号长期 research markdown。**
3. **把热点能力继续放在独立的 `HotspotScoutAgent / XHotspotScoutService` 上。**
4. **热点先入库、再研究、再转任务、最后按 72 小时窗口清理。**

一句话版：

> 保留账号长期 `ResearchAgent`，独立演进热点链。这条路现在已经跑通主干，后续应该做增强，不该再回头把两类职责混在一起。
