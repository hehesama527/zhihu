# 知乎 Agent 全自动风控优化文档

文档日期：2026-04-06  
负责人：二牛  
文档目标：在“必须全自动，且不把 IP 作为主优化变量”的前提下，重新定义知乎矩阵链路的风控问题，并形成后续改造基线。

---

## 一、前提先定清楚

这份文档不讨论“要不要全自动”。

这个前提已经确定：

1. 知乎链路必须走全自动。
2. 发布、调度、审核、熔断这些主链路必须自动推进。
3. 人工登录恢复暂时视为现实约束，可以保留为最终兜底，不作为当前主要优化对象。
4. 当前网络出口条件视为既定约束，不再把 IP 改造作为本轮主方案。
5. 后续改造目标不是“把人工彻底消灭”，而是把当前链路从“可运行”提升到“可长期自动运行，且不会整组连坐”。

但也要把边界说清楚：

1. 全自动不等于可以无视平台风控。
2. 全自动不等于遇到强校验时还要强行推进。
3. 真正可接受的口径应当是“正常路径自动推进，风险路径自动熔断、自动隔离、自动告警，极少数账号登录恢复仍可保留人工兜底”，而不是“无论发生什么都继续发”。

---

## 二、这次事故应该怎么定性

当前现象不是“某一篇内容被打回”，而是“矩阵内多个账号被平台集中识别并封禁”。

这类事故的优先判断顺序，不应该先从单篇内容质量入手，而应该先看共享环境画像。

更直接地说：

1. 如果是单账号、单篇内容问题，更常见的表现是个别回答异常、单号限流、单号进入验证。
2. 如果是多个账号在接近时间窗口内一起出事，更像是平台把这些账号识别成了同一个运营集群。
3. 当平台已经形成“同源账号群”的判断后，内容、IP、设备、浏览器资产、发布节奏、登录行为、账号身份切换等信号会被一起计分，而不是单独判断。

本次事故应定义为：

`知乎矩阵在共享运行环境下触发了平台级关联风控，表现为账号群体性封禁。`

---

## 三、本轮先不把 IP 作为主优化变量

先把边界说清楚：

1. IP / 网络出口在平台风控里可能有影响。
2. 但当前条件下，IP 改造不是可稳定落地、可立即推进的方案。
3. 本轮文档不再围绕“换 IP”“拆出口”“补路由资源”展开。

因此，这份文档的工作口径调整为：

`把 IP 视为当前环境常量，只优化系统自身可控变量。`

这意味着：

1. 不再把“如何换网络”写成主动作。
2. 重点转到账号资产隔离、浏览器资产纯净度、调度节奏、异常熔断和矩阵同构性。
3. 即使未来网络条件变化，也只把它当补充项，不作为当前系统设计的核心前提。

---

## 四、事故定性不变，但解释口径收窄到可控项

这次事故仍然要定义为“共享运行环境下触发的平台级关联风控”。

但从当前执行层面看，本轮更应该抓住的是这些可控变量：

1. 多账号共用同一台主机
2. 多账号共用同一浏览器通道
3. 多账号沿用历史 Profile 资产
4. 浏览器自动化动作高度一致
5. worker 固定节奏轮询
6. 多账号在近时间窗口内形成明显矩阵波峰
7. 题材、人设、产品承接方式高度同构

一句话说：

`不再尝试解释“网络为什么有问题”，而是先修正“系统自己把矩阵做得过于整齐、过于共享、过于可关联”的部分。`

---

## 五、问题收敛方式改成“共享环境降关联”

当前更合理的判断是：

`真正的问题不是某一个外部变量，而是知乎矩阵当前呈现给平台的是一套过于统一、过于共享、过于可关联的运行画像。`

所以后续文档和改造统一写成：

`全自动前提下的共享环境降关联方案`

---

## 六、当前链路里与“生产级全自动”冲突的地方

### 6.1 人工恢复存在，但不是当前主要矛盾

当前系统遇到 `manual_login_required`、`session_expired`、`account/unhuman` 时，正式处理路径仍然是人工介入。

如果从理想定义看，这和“彻底无人介入”是冲突的。

但结合当前约束，这一项可以先接受，不作为现阶段第一优先级。

当前更重要的不是把人工恢复抹掉，而是先解决：

1. 为什么会整组一起触发风险
2. 为什么单个账号异常会扩散到整组账号和整台主机
3. 为什么系统在风险升高前没有自动降载和隔离

所以这里的口径调整为：

1. 风险出现前尽量提前识别
2. 风险一旦出现，自动停发、自动隔离
3. 避免把单账号风险扩散到整组账号
4. 被隔离后的个别账号仍允许进入人工恢复兜底

### 6.2 Profile 隔离不等于环境隔离

当前系统已经做了账号级 `profileDir`，这很重要，但这只是隔离的一半。

在本轮不处理 IP 的前提下，当前至少要把以下三层边界补齐：

1. 账号边界
2. 浏览器资产边界
3. 调度节奏边界

现在的短板主要在后两层。

### 6.3 当前观测数据不足以还原“封禁前 10 分钟发生了什么”

目前系统能看到任务状态、截图、工具 trace、技能 trace，但还缺关键环境观测：

1. 当时账号走的公网出口是谁
2. 封禁前 30 分钟是否出现同主机、同浏览器通道、同时间窗连续登录检查
3. 是否出现多账号连续触发验证
4. 是否出现历史 Profile 混用或身份错配
5. 是否出现批量恢复后立刻批量再发

没有这些观测，就只能凭经验猜。

## 七、后续优化原则

在“必须全自动”的前提下，知乎链路后续必须遵守以下原则。

### 7.1 原则一：账号隔离必须升级为环境隔离

目标不是“每个账号一个 Profile”。

目标应升级为：

`每个账号都绑定一套稳定、可归因、可观测的运行环境。`

这套环境至少要包含：

1. `accountId`
2. `profileDir`
3. `browserChannel`
4. `hostId`
5. `riskDomain`
6. `lastKnownEgressFingerprint`

### 7.2 原则二：自动化链路要能自动熔断，不要自动硬顶

后续系统不应在出现明显挑战页、验证页、账号异常页后继续尝试推进发布。

正确口径应该是：

1. 单账号进入异常，立即冻结该账号
2. 同一风险域下短时间多账号异常，冻结整个风险域
3. 同主机下多账号集中异常，冻结整机知乎发布任务
4. 先保护账号资产，再谈恢复

### 7.3 原则三：不要靠“伪装正常浏览”解决结构性问题

后续优化不能把方向写成“增加一些看起来像人的动作”。

这种思路不稳，也容易把问题做偏。

真正应该解决的是：

1. 共享环境过强
2. 发布节奏过密
3. 风险域与账号绑定关系不清晰
4. 风险没有在平台升级前被自动切断

### 7.4 原则四：先补观测，再补调度，再补扩容

如果没有环境观测，就不应该继续扩矩阵。

顺序必须是：

1. 先能看清
2. 再能控制
3. 最后才谈放量

## 八、目标架构口径

后续知乎全自动链路建议从“账号中心”升级为“账号执行单元”。

每个账号执行单元至少包含：

1. 账号身份：`accountId`、`zhihuUserName`
2. 浏览器资产：`profileDir`、`browserChannel`
3. 运行宿主：`hostId`
4. 风险域：`riskDomain`
5. 风险状态：`ready / cooling_down / blocked / quarantined`
6. 观测信息：`lastSeenIpHash`、`lastSeenRegion`、`hostHealthScore`

这里最关键的新增字段是：

1. `riskDomain`
2. `lastSeenIpHash`
3. `hostHealthScore`
4. `cooldownUntil`

后续 worker 调度应以“账号执行单元”为最小粒度，而不是只看账号本身。

## 九、P0 改造项：先把看不见的问题看见

这一层不改，后面所有判断都不稳。

### 9.1 增加账号级网络观测

每次执行以下动作前后，都记录一次网络观测：

1. 登录检查前
2. 打开问题页前
3. 点击发布前
4. 发布校验后
5. 出现挑战页后

每次至少记录：

1. `accountId`
2. `hostId`
3. `profileDir`
4. `riskDomain`
5. `egressIpHash`
6. `region`
7. `observedAt`
8. `jobId`
9. `stage`
10. `result`

注意：

1. 生产库里建议落哈希和元数据，不必裸存原始公网 IP。
2. 目标是追踪一致性和关联性，不是做网络审计系统。

### 9.2 增加“风险域级事故”识别

当前系统更偏账号级异常。

后续要新增两类事故：

1. `risk_domain_spike`
   定义：同一 `riskDomain` 下，30 分钟内 2 个及以上账号进入 `session_expired` 或挑战态
2. `host_correlation_risk`
   定义：同一主机下，多账号在短窗口内连续进入异常态

一旦触发，系统不应继续拿同一风险域下的其他账号去试。

### 9.3 增加全局熔断

新增三个熔断开关：

1. 账号级熔断
2. 风险域级熔断
3. 主机级熔断

推荐口径：

1. 单账号出现挑战页，冻结该账号 12 小时
2. 同风险域 2 个账号 30 分钟内出现挑战页，冻结该风险域 24 小时
3. 同主机 3 个账号 60 分钟内出现挑战页，冻结该主机知乎链路，等待人工复盘

这里的“人工复盘”不等于人工继续发，而是人工确认系统策略和环境状态。

## 十、P1 改造项：把可控变量真正改掉

既然本轮不把 IP 当主变量，那 P1 层就集中改系统内部真正能控的东西。

### 10.1 先把账号执行单元补完整

建议为知乎账号新增：

1. `riskDomain`
2. `hostId`
3. `cooldownUntil`
4. `lastRiskAt`
5. `lastSeenIpHash`
6. `lastSeenRegion`

这里的 `riskDomain` 不是网络方案，而是系统里的风险分组主键。

如果今天所有账号都跑在同一台机器、同一环境下，那也应该显式写成同一个 `riskDomain`，而不是默认假装它们互相独立。

### 10.2 调度约束建议

worker 后续调度时要增加这些硬约束：

1. 同一 `riskDomain` 在一个冷却窗口内只允许一个账号进入发布阶段
2. 同一 `riskDomain` 下已有账号进入 `manual_login_required` 或挑战态时，其他账号暂停调度
3. 同一主机连续出现多账号异常时，优先冻结整机知乎链路
4. 批量恢复后不允许立刻批量再发
5. 同一账号在进入冷却前，不允许重复尝试推进发布

### 10.3 运行时怎么改

这一层主要改浏览器资产和执行节奏。

第一层，账号模型：

1. `packages/shared` 补知乎账号的 `riskDomain`、`cooldownUntil`、`lastSeenIpHash`、`lastSeenRegion`
2. `packages/core` 的 account repository 补读写

第二层，浏览器运行时：

1. `PlaywrightToolRuntime` 启动会话前先校验账号是否处于冷却
2. 会话建立后立即记录一次环境观测
3. 避免多个账号连续复用同一批机械动作模板

第三层，worker 调度：

1. worker 取可执行账号时，先判断账号状态
2. 再判断 `riskDomain` 状态
3. 再判断主机状态
4. 任一不健康，都不进入发布

### 10.4 Web 和 API 怎么改

API 至少要新增：

1. 账号冷却状态查询接口
2. 风险域状态查询接口
3. 风险域冻结/解冻接口
4. 最近环境观测接口

Web 至少要新增：

1. 账号详情里显示 `riskDomain`
2. 显示最近一次 `egressIpHash`
3. 显示当前是否处于账号冷却
4. 显示当前风险域是否冻结
5. 支持按风险域过滤异常任务

### 10.5 明确禁止的做法

既然本轮不做 IP 方案，那后续不要把注意力带偏：

1. 不要把“换网络”当成本轮主动作
2. 不要把“多号共享同一环境，只是错开几分钟”当成风险控制
3. 不要在账号刚恢复后立刻补发积压任务
4. 不要继续让历史脏 Profile 和新账号混跑

## 十一、P1 改造项：把固定机械节奏改成可控调度

当前系统已有排期随机化，但还不够。

需要重点改造的是系统性机械节奏。

### 11.1 worker 轮询不应长期固定

当前 `WORKER_INTERVAL_MS` 是固定值，容易形成稳定的机器节拍。

后续建议改成：

1. 基础间隔
2. 加小幅抖动
3. 不同阶段有不同节奏

这里的目的不是“伪装成人”，而是避免系统级齐步走，减少自造突发。

### 11.2 风险域级冷却要独立于账号级冷却

后续至少要有三层冷却：

1. 账号级冷却
2. 风险域级冷却
3. 主机级冷却

否则同一个风险域已经不健康，系统还会继续用它去推进其他账号。

### 11.3 登录检查不要和发布高峰混在一起

当前链路里登录检查、发布推进、失败恢复都可能落在相近窗口。

后续建议把动作拆成：

1. 低频账号健康检查
2. 发布前短检查
3. 发布后验证

而不是把所有动作都压在同一个时段。

---

## 十二、P2 改造项：降低矩阵内同构性

虽然本次优先级最高的是共享环境，但矩阵内内容和操作形态的同构性也要降。

### 12.1 题材同构要控制

如果多账号在近窗口内都发相近题材、相近结构、相近产品承接，平台更容易把它们归成同一运营组。

后续要控制：

1. 同日同主题占比
2. 相同产品提及密度
3. 相似标题结构
4. 相似结尾和相似 CTA

### 12.2 发布批次不要形成明显矩阵波峰

同一时间段如果多个账号连续进入发布、验证、异常恢复，很容易形成系统波峰。

后续应在调度层避免：

1. 同风险域短时多账号连发
2. 同主机短时多账号登录检查
3. 同时批量恢复后立刻批量再发

---

## 十三、验证方案

后续改造不能一把梭。

建议分三阶段验证。

### 阶段 0：只补观测，不放量

目标：

1. 补齐网络观测
2. 补齐风险域级事故识别
3. 补齐熔断

通过标准：

1. 能准确回答“某次封禁前 10 分钟每个账号属于哪个风险域”
2. 能准确回答“是否多个账号共享出口”
3. 能准确回答“是否在同一风险域内形成异常聚集”

### 阶段 1：单账号单风险域验证

目标：

1. 只拿一个账号做完整自动发布
2. 风险域固定
3. 环境不漂移

通过标准：

1. 连续 7 天无 `session_expired`
2. 无挑战页
3. 发布成功率稳定

### 阶段 2：小规模矩阵验证

目标：

1. 扩到 2 到 3 个账号
2. 明确各账号与风险域绑定关系
3. 验证风险域级熔断是否工作正常

通过标准：

1. 未出现同窗口双账号异常
2. 未出现整组连坐
3. 风险域级熔断触发后不会继续放大事故

---

## 十四、成功标准

当以下指标同时成立，知乎全自动链路才算进入下一阶段：

1. 连续 14 天无矩阵级集中封禁
2. 单账号 `session_expired` 率明显下降
3. 同风险域多账号关联异常下降到接近 0
4. 所有发布任务都能回溯到具体 `hostId + riskDomain + egressIpHash`
5. worker 在风险场景下能自动熔断，而不是继续尝试

## 十五、当前结论

截至 2026-04-06，当前知乎链路的问题，不应再定义为“内容像不像 AI”。

更准确的结论是：

1. 本次事故大概率属于共享环境关联风控。
2. 本轮不把 IP / 网络出口作为主优化变量。
3. 问题不能收敛成“换 IP”。
4. 真正要改的是：账号、Profile、风险域、调度节奏、事故熔断、矩阵同构性这整套共享环境画像。
5. 当前系统距离“生产级全自动”最大的差距，不是写作链路，而是环境隔离和风险观测。

一句话收尾：

`如果继续维持“单机共享环境 + 账号只隔离 Profile、不隔离风险域 + 风险后再人工补救”的口径，知乎矩阵即使能短期恢复，也大概率还会再次出现整组连坐。`
